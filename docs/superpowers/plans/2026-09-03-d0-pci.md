# D0 — PCI enumeration

**Spec:** `docs/superpowers/specs/2026-09-03-pci-and-network-design.md`

**Goal:** the kernel can find out what PCI devices exist, where their
registers are, and which interrupt line they use.

**Status:** DONE.

## What was built

| File | Role |
|---|---|
| `kernel/arch/io.h` | `outl`/`inl` — config space is dword-wide, and a byte access to 0xCFC reads something else entirely |
| `kernel/drivers/pci/pci.h` | `struct pci_device`, register offsets by name, the lookup and config-access interface |
| `kernel/drivers/pci/pci.c` | brute-force enumeration, BAR decoding, `pci_selftest` |
| `kernel/kernel.c` | `pci_init(); pci_selftest();` immediately before `ata_init()` |
| `Makefile` | `kernel/drivers/pci` in `KERNEL_DIRS`, `[pci] ALL PASSED` in `REQUIRED_MARKERS` |

## What the machine actually has

```
[pci] 00:00.0 8086:1237 class=06:00:00 irq=00
[pci] 00:01.0 8086:7000 class=06:01:00 irq=00
[pci] 00:01.1 8086:7010 class=01:01:80 irq=00 bar4=io:0000c040/00000010
[pci] 00:01.3 8086:7113 class=06:80:00 irq=09
[pci] 00:02.0 1234:1111 class=03:00:00 irq=00 bar0=mem:fd000000/01000000 bar2=mem:febb0000/00001000
[pci] 00:03.0 8086:100e class=02:00:00 irq=0b bar0=mem:feb80000/00020000 bar1=io:0000c000/00000040
[pci] enumerated 06 functions
```

Two things worth recording, because they are the next two milestones
looking back at us:

- **8086:100e is the e1000**, already attached, at IRQ 11 with a 128 KiB
  MMIO BAR. D1 has its device; nothing needs to be added to the QEMU
  command line to start.
- **8086:7010 is the PIIX3 IDE controller** (class 01:01), the same
  controller the PIO driver is currently talking to through fixed legacy
  ports. Its bus-master DMA registers are that `bar4=io:c040/10`. The
  `[ata] BSY never cleared` timeouts have a documented address now.

The BAR decode has an independent check: `1234:1111 bar0 = fd000000`,
size 16 MiB, is the QEMU VGA framebuffer — the same address the VESA
driver is already writing pixels to, arrived at by a completely
different route.

## Proving the test can fail

Each detector was broken deliberately and the failure observed, then
reverted.

| Break | Result |
|---|---|
| enable bit cleared in `config_address` (`0x80000000` → `0`) | `enumerated 00 functions` / `FAILED: no PCI functions found at all` |
| BAR size computed as `~mask + 3` | `FAILED: BAR size is not a power of two` |
| command-register write-back drops its low half | `FAILED: config space did not round-trip` |
| known-id check looks for `8086:7999` | `FAILED: no PIIX3 ISA bridge (8086:7000)` |

The round-trip break is the one that mattered most to prove: a read-only
test would pass against a completely wedged CONFIG_ADDRESS, because the
data port keeps returning whatever the last programmed address held.

## Decisions worth remembering

- **BARs are only sized on type 0 headers.** A bridge's type 1 header
  has two BARs at the same offsets with a different meaning, and its
  window registers live where a device's BAR 2–5 do. Writing all-ones
  into those is the "harmless probe" that unmaps the disk.
- **The BAR restore is not optional and not deferred.** Every probe
  writes `0xFFFFFFFF` and puts the original back before the next read.
- **No lock.** Enumeration runs on the BSP before the APs start and the
  table is read-only afterwards. A driver that starts writing config
  space concurrently with another is when this needs one.
- **64-bit BARs consume two slots**, and a 32-bit BAR's mask is extended
  with ones in the high half before `~mask + 1`, or the size runs off
  the top of the word.

## Not done, deliberately

No MSI, no ECAM, no capability list walking, no bridge recursion, no
driver-binding framework. Each is infrastructure for a driver that does
not exist; `pci_find_id` and `pci_find_class` are what D1 needs.
