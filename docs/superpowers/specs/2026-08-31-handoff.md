## 1. The one thing that needs finishing

**There is an uncommitted fix in `kernel/tlb.c` that was still being
verified when the session ended.** It is believed correct and the tree
builds and passes, but it has not been through enough runs to be
trusted, because the bug it fixes appears roughly **once in ten boots**.

### The bug

`tlb_defer_free()` used a fixed 64-entry array of frames awaiting a TLB
shootdown. When that array filled, it performed an emergency
`tlb_shootdown(0)` on the spot.

That is illegal. `vma_munmap` unmaps **while holding the process's
`mm_lock`**, and `tlb_shootdown` opens with:

```c
if (lock_held_depth() != 0) {
    lock_panic("tlb_shootdown with a lock held", "tlb", 0);
}
```

— because a shootdown target spinning on that same `mm_lock` with
interrupts disabled can never acknowledge, so the sender would wait
forever. Tearing down an address space defers hundreds of frames (every
user page plus every page-table frame), so the array fills easily once
several processes exit at once.

Observed as:

```
[lock] PANIC: tlb_shootdown with a lock held acquiring=tlb holding=(none)
```

### The fix (uncommitted, in the working tree)

The queue is now unbounded: a 256-entry fast-path array plus a linked
overflow list. The overflow node is `kmalloc`ed **before**
`deferred_lock` is taken — that lock is the innermost rank in the
kernel and nothing may be acquired beneath it. If the allocation fails,
the frame is deliberately **leaked** with a log line, because handing
it back to `pmm` is the exact memory corruption the whole mechanism
exists to prevent.

`tlb_flush_deferred` drains the array one entry at a time under the
lock rather than copying it out: a 256-entry copy is 4KiB, too much for
a 16KiB kernel stack that interrupts nest on, and making the copy
`static` instead would let two draining CPUs clobber each other.

### What to do

```bash
git diff kernel/tlb.c        # review the fix
for i in $(seq 1 15); do make test 2>&1 | grep -E "PASS:|FAILURES|MISSING|BOOT DID"; done
```

Fifteen consecutive green runs is the bar — the failure rate was about
1 in 10 before the fix, and 4 runs had passed when the session ended.
Then commit `kernel/tlb.c`, `docs/abi-compatibility.md` and
`docs/superpowers/specs/2026-08-31-ipc-tls-networking.md` together.

If it fails again, the panic line names the lock. See §4.

## 2. What landed, and is green

Phase 11 (work stealing) and Phase 12 (IPC, TLS, networking) are both
complete and committed. `make test` runs 13 userland suites plus the
kernel selftests on 4 CPUs.

**Phase 11 — work stealing**, resolving
`2026-08-30-work-stealing-problem.md`. Full write-up in
`2026-08-30-work-stealing-resolution.md`. Threads now migrate between
CPUs, user threads included.

**Phase 12 — this milestone**, written up in
`2026-08-31-ipc-tls-networking.md`:

- **Syscall table.** One handler per call, dispatched through a table
  indexed by the syscall number, with an integrity selftest. 53
  syscalls; an unimplemented number returns `-ENOSYS`.
- **futex**, Linux-shaped, `WAIT`/`WAKE`, keyed by physical address.
- **POSIX semaphores, pthread mutexes and condition variables** on top
  of it, in `lib/`.
- **Pipes**, and the file-descriptor ops table they needed.
- **Thread-local storage**: `arch_prctl`, per-thread FS base restored
  on every context switch, and a real SysV entry stack with argc,
  argv, envp and an auxiliary vector.
- **A loopback network stack**: IPv4 and UDP with real checksums, and
  AF_INET datagram sockets.
- **MPI**, a subset of MPI-1 over those sockets.
- **`spawnv`** and **`fcntl`** (F_GETFL/F_SETFL).

Every API and every divergence from POSIX/Linux is in
`docs/stdlib.md`. The Linux-ABI inventory is in
`docs/abi-compatibility.md` (**uncommitted — refreshed for this
milestone**).

## 3. What to do next

In rough order of value:

1. **`O_CREAT` has the wrong value.** NeoOS 0x100, Linux 0x40. A
   program compiled against Linux headers silently fails to create
   files. It has been called out for two milestones. It costs one
   constant in `kernel/syscall.c` and `lib/include/fcntl.h`.

2. **The `stat` family and `struct dirent`.** These are now the two
   largest ABI gaps — the second or third call almost any real tool
   makes. `struct dirent` currently has a 13-byte fixed name and no
   inode, offset or record length; nothing about it matches Linux, and
   a shim cannot paper over it.

3. **`select`/`poll`.** The most conspicuous thing missing from the
   socket work: a program waiting on several descriptors currently
   needs a thread each.

4. **TCP.** The socket layer, the file-ops seam and the loopback device
   are all ready. It is a protocol implementation, not plumbing.

5. **`clone` and `clock_gettime`.** What a libc reaches for after the
   above.

Longer-term, the roadmap
(`2026-08-27-roadmap-architecture-design.md`) still has dynamic
linking, modules, PCI/DMA, and the block layer ahead.

## 4. Tools, and one thing worth knowing

- `make test` — headless QEMU, 4 CPUs, COM1 to `build/serial.log`.
  Fails on any `FAILED` line, a missing boot marker, or a missing suite
  marker (`REQUIRED_MARKERS` in the Makefile). **`BOOT_TIMEOUT` is now
  150 seconds**, up from 60: the suite roughly doubled, and when
  `mpitest` (spawned last) stopped getting CPU time before the timeout
  it produced no output at all, which looks exactly like a hang.

- `make test SMP_CPUS=1` — the fastest way to tell an SMP bug from a
  general one. Every SMP selftest fails here by design.

- **The lock rank checker** turns an ordering error into a panic naming
  both locks.

- **Spinlocks now panic by name after a bounded spin** (added this
  session, `kernel/lock.c`). Every spinlock here is held with
  interrupts disabled for a bounded number of instructions, so a long
  wait is a cycle, not contention.

  This is worth knowing about because of how the bug in §1 presented
  before it existed: **no output, no panic, and not even a timer tick**
  — the stuck CPU was spinning with `IF` clear, so it could not even
  take a clock interrupt. A serial log with zero `[timer] tick=` lines
  in a 150-second run was the entire evidence base. If a boot ever
  looks like that again, the missing tick lines are the tell: some CPU
  is spinning with interrupts off.

- `x86_64-elf-addr2line -f -e build/kernel.elf <rip>` on the `rip=` in
  an exception dump, then `objdump -d --start-address=...`.

## 5. Two loose threads, recorded so they are not rediscovered

**The SIGSTOP/SIGCONT race test is a smoke test, not a proven
reproducer.** `sigtest`'s stop/continue loop passes with the fix
reverted, both before and after user threads could migrate — the
vulnerable window is a few microseconds wide and ten rounds do not land
in it. The fix (in `signal_do_stop`/`signal_do_continue`) rests on
construction. Making the test deterministic needs a deliberate widening
of that window behind a debug switch.

**`smptest` reports rather than asserts which CPUs its threads ran on.**
Whether eight threads get spread depends on whether another CPU happens
to be idle while they run, and with a dozen programs in the boot there
often is not one. The invariant is asserted in the kernel instead, by
the steal selftest's user-migration counter.
